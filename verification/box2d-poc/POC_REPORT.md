# 《磁力小车》Box2D 服务端验证

2026-11-18，基线为远端 main 与本地 main 共同指向的 `e4c7af9903ff306b1066474f4e4bdf9eb41e40e8`。实验分支为 `poc/box2d-native`。

**建议当前保留 Lua。** 矩形偏心碰撞产生可测的旋转，冲量可传到第三辆车；3× 步进对高速车车交会也有收益。物理运行成本在这台机器上付得起，但现有客户端无法表达独立车身旋转，替换碰撞器还会改变已有命中时序。若游戏设计明确需要侧撞旋转，后续候选是保持 20 Hz 游戏规则与 10 Hz 广播，单 tick 内步进 3 次。

## 运行路径及边界

* Docker 在 Apple M6 上运行 Linux arm64。容器限制 2 CPU、512 MiB，与仓库 compose.yaml 对齐。cgroup 实读 cpu.max 为 200000/100000，memory.max 为 536870912。没有访问生产主机。硬件、镜像 ID、Skynet 二进制及源包哈希见 [环境记录](results/environment.txt)。
* Skynet 镜像修订为 `f1baee5051108fce40588738f4a5960f12edea97`，嵌入 Lua 5.5.1。使用项目随附 Lua 5.5.1 头文件，GCC 14.2、-O2、PIC，在 Linux 编译原生模块；模块入口执行 luaL_checkversion。Box2D v3.1.1 固定在 `8c661469c9507d3ad6fbd2fea3f1aa71669c2fe3`。
* server/main.lua 每 5 个 Skynet 厘秒唤醒，Rooms:advance 串行遍历各房间，GameClock 以 50 ms 固定步长推进。每次唤醒每房最多追 5 步，超出的运动步丢弃，超时时钟继续走。每 10 厘秒发布状态，每秒更新大厅目录。项目配置 4 个 Skynet 工作线程，某时刻同一个房间管理服务只由一个线程执行。
* 实验在真实 snlua 中 require 共享库。Game 照常处理输入、冲刺时长、攻击方向、眩晕、保护、掉落、路径拾取与结算。仅在实验服务替换 vehicle_collision.resolve；每个活动房间拥有一个零重力 World、8 个动态矩形、96 段近似圆形外墙和与地图一致的站体。长度比例为 100 游戏单位/米，矩形半长、半宽为原碰撞半径的 0.90、0.62。这是实验形状选择。转向、油门、松油阻尼由 Lua 计算。
* 每次 resolver 批量输入全部车辆速度，回传位置、线速度、车身角、角速度、接触开始事件及子步路径。3× 调用三次 b2World_Step(dt/3, 1)，逐次提取事件；通常每房每 tick 跨一次 Lua/C，冲刺在 tick 中途耗尽时原 Game 会先切片。业务收到事件时以所在子步起点近似接触时刻，进攻分类使用子步入射速度。多个子步的命中统一回调，子步内没有精确 TOI 回调；规则施加的后坐速度对后续切片生效。
* World 串行运行，未创建房间专用线程。100 次经 Rooms.handle 建房、开局、断开、超时移除后，两次 GC 后存活 World 引用为 0。另做 1,000 次显式创建/销毁，在第二个仍存活的 World 中检查车身状态，位置保持独立。原生崩溃仍可终止整个 Skynet 进程。短测不能证明长期无内存泄漏。

| 首次几何重叠 / Box2D begin / 业务掉落 / v2 状态发布 / 首次重新拾取，逻辑 tick | 1 / 2 / 2 / 2 / 15 | 1 / 1 / 1 / 2 / 14 |

810 是默认参数下空载最高冲刺速度。高速断言检查中心前后顺序及墙界，允许求解器容差内的接触重叠；2200 是超默认速度探针。Box2D 的 bullet 选项对另一 bullet 不提供连续碰撞保证。1× 的时序差发生在接触事件形成之前，业务回调收到 begin 后同 tick 掉落。3× 可以在游戏 tick 内的后续子步报告 begin。

链路测试使用原 Game:drop 生成三枚电池，检查受撞者 cargo、hitSeq 以及实际编码的 v2 消息，锁定期内拾取序号保持不变。为验证先掉后拾的顺序，夹具将一枚真实掉落物放回受撞车附近并使其落地，保留原解锁时刻。该用例只有一次掉落。另一个满载车被压在墙边的 100 tick 用例中，两种模式均仅掉落一次；攻击者持续给油，业务接触标记连续保持 98 / 99 步，跨过 1.6 秒保护期后仍无重复掉落。静止接触持续 100 步只收到一次 begin。持续相向加油则可能分离再接触（1×/3× 各 12/9 个 begin），业务必须继续做接触去重。松油后的连续 15 步速度单调下降。详细数值见 [Skynet 断言日志](results/test.log)。

### 与原测试的兼容性

在历史夹具配置下原样运行 10 个规则测试文件。Lua 10/10；1× 和 3× 各 3/10，通过掉落物拾取、房间游戏生命周期、移动协议测试。每文件遇首个失败停止，比例不代表代码行覆盖率。

* 三个碰撞文件在原圆形恰好应命中或眩晕的位置失败，矩形轮廓与离散接触时刻共同改变游戏手感。不能把原有命中规则的代码复用解释为行为完全兼容。
* test_game 的过期输入停止断言失败；松油滑行和夹具中的直接 Lua 坐标写入都与旧预期有差异。test_pickup_seq 把 Lua 玩家直接移到站内，World 未跟随传送，入站结算断言失败。
* test_fast_movement 对满载位移要求 1e-9 误差，原生单精度结果未通过。test_station_collision 直接传入 100 ms 步长，超过此实验适配器支持的 50 ms 游戏切片。该文件后续断言未执行。
* 结论限于已覆盖的命中、锁定与拾取；没有通过原套件的替换兼容验收。逐项首个失败见 [Lua](results/compat-0.log)、[1×](results/compat-1.log)、[3×](results/compat-3.log)。

### 原 H5 的侧撞

在本机 Edge 中用原 H5 驾驶第一辆车向右偏心撞上静止车，使用真实 main.lua、WebSocket 与现有协议，运行到 100 秒结算。命中快照前后读取 H5 自身 Motion.sample，本车从 (−83.14, 48.00) 修正到 (−80.79, 49.23)，约 2.65 游戏单位，x 方向仍向前。本次撞击未见位置大幅向后回弹。作为补充，早期适配器的被撞方测试在静止时修正约 12.88 单位。两次均为本机低延迟单例，不能代表真机和广域网抖动下的分布。

主动侧撞瞬间，服务端本车驾驶朝向 0、车身角 −0.0267 rad、角速度 −1.969 rad/s；另一辆车角速度 −0.571 rad/s。Game:snapshot 只发布原 angle，客户端沿用圆形预测，无法显示权威的独立车身朝向。本次确认了位置修正和结算，未验证客户端旋转手感。[浏览器记录](results/h5.log) · [服务端记录](results/h5-server.log)

## 性能测量口径

每组新起一个 Skynet 进程，按 32、16、8 房顺序测试，每房 8 个协议 v2 玩家。相同 mapScale=2、站点、资源配置、seed=1701，输入由每房逻辑步序号和座位号生成，持续转向且周期冲刺。不同物理结果会改变后续状态及事件量。基线原样使用 Lua 圆形连续碰撞器；1× 和 3× 分别每游戏步进行一次 50 ms 或三次约 16.67 ms 的世界推进，各以一个求解子步运行。三组游戏时钟、广播时钟、计时与输出工具相同。

按 server/main.lua 的唤醒、过期目标重置和广播节拍，在单个真实 snlua 中调用原 Rooms:advance、GameClock、Game、Rooms:broadcastStates，包括 v2 快照投影、JSON 编码及向八个连接排队，然后 drain。输入直接回放到 Game:input。**范围到服务端广播队列**；没有压入 WebSocket 收包、每包 Rooms:handle 的额外 advance、网络发送/背压、真实客户端或 AI。H5 单局另测。该数据适合对比此处房间服务成本，对外在线容量仍需端到端网络负载验证。

每组预热约 3 秒，随后按单调墙钟测量至少 60 秒。进程 CPU 为进程 CPU 秒数 / 墙钟秒数，100% 代表一个核。热点列为 /proc/self/task 中最忙 OS 线程的区间 CPU；串行服务会在四个 Skynet 工作线程间迁移。另用包含快照的整轮时间判断中心服务是否吃满一个逻辑步预算。整轮含输入回放，物理列是单房单次 resolver 的墙钟时间，含绑定、路径与接触回调。时间分位以 nearest-rank 统计。

调度延迟是实际唤醒减预定唤醒，Skynet 时钟精度 10 ms。漏步计算每次超过 5 步的丢弃数；追帧计算一次唤醒内第 2 至第 5 步的数量。所有同起点房间在同一 now 推进，下表按共享时钟计数，乘房数可得房间步数。峰值 RSS 取测量结束时 VmHWM（含建房峰值），销毁后 RSS 在清空房间管理器及样本、两次 GC 后取 VmRSS。中间导出 trace 会分配字符串，且分配器可能保留内存，因此后一读数可以高于前者。每组原始采样及汇总均在 [results](results/)。

### 八车独立物理微基准

模式 0 / 1 / 3 分别是 Lua / Box2D 1× / Box2D 3×。32 房使用关闭本实验 H5、停止编译后的独立复测。首轮 32 房的进程 CPU 分别为 33.78%、32.02%、41.95%，整轮 P99 为 34.27、37.93、41.77 ms，全部零漏步。两轮 CPU 排序一致，尾耗时有波动，尤其 1× 相对 Lua 的 P99 排序发生了变化。[首轮日志与采样](results/initial32/)

**32 房成本。** 相对 Lua，1× 的进程 CPU 减少 3.73 个百分点（相对 −10.7%），3× 增加 5.71 个百分点（相对 +16.4%）。3× 的整轮 P99 为 33.98 ms，Lua 为 33.96 ms；二者在本次复测中非常接近。3× 每房需要更多求解及路径段处理。轨迹、接触及拾取会随物理模型分化，整轮差值包含这些下游开销。不同房数下单位成本与 CPU 比例也有波动，不能把单次百分比当作固定换算系数。

**最大实测稳定档位为 32 房 × 8 车。** 以测量窗口内无丢弃逻辑步、整轮 P99 小于 50 ms 为标准，三组均通过，且没有追帧。32 也是当前 Rooms.handle 的建房上限。中心服务未观察到单核饱和，本轮没有增加 Room Worker。覆盖范围为本机容器内 60 秒级回放、真实房间与快照路径；尚缺生产端到端网络负载、长时间 soak 和目标主机数据。

**取舍。** 1× 已经能表现旋转，但可能把接触延至下个游戏 tick，超默认速度对撞还出现过中心重合。3× 更符合希望保留旋转与高速交会精度的玩法；本次 32 房测量有时间余量。当前客户端既不预测矩形接触也不表现独立车身角，原有圆形命中边界、Lua 与原生状态重置、二进制 ABI 都增加了验证和维护工作。以现有玩法和协议，收益尚不足以支持切换默认实现。
